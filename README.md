# Realtime Fintech Dashboard

A small Angular application that displays live simulated market data generated by a candidate-written WebAssembly module running inside a Web Worker.

## Links

- Repository: https://github.com/dmytrorozhkov/realtime-fintech-dashboard
- Live demo: https://realtime-fintech-dashboard.pages.dev/

## Features

- Live dashboard for fictional financial instruments
- Last traded price
- Bid-ask spread
- Cumulative trading volume
- Volume-weighted average price (VWAP)
- Order-book imbalance
- Pause and resume without resetting accumulated values
- Validated producer settings
- Explicit Apply action that starts a new run
- Protection against stale results from previous runs
- Automatic UI snapshot throttling
- Unit tests for metrics, settings, worker coordination, and generator behavior

## Architecture

```text
AssemblyScript producer
        |
        | compiled to producer.wasm
        v
Web Worker
  - loads and executes Wasm
  - schedules generated batches
  - decodes the numeric transport format
  - aggregates every market update
  - throttles UI snapshots
        |
        | typed messages with runId
        v
ProducerClientService
  - owns the single worker instance
  - exposes Angular signals
  - handles Pause and Resume
  - rejects stale run results
        |
        v
Dashboard and Settings
```

The worker is owned by a root Angular service, so navigation does not create additional producers.

## Market update format

The Wasm producer returns a flat `Int32Array`. Each market update contains seven values:

| Index | Value                |
| ----: | -------------------- |
|     0 | Instrument index     |
|     1 | Trade price in cents |
|     2 | Trade quantity       |
|     3 | Bid price in cents   |
|     4 | Ask price in cents   |
|     5 | Bid quantity         |
|     6 | Ask quantity         |

A flat numeric format avoids JSON serialization inside Wasm.

The generator retains a current price for every instrument. Prices evolve from their previous values, remain positive, and every trade price is selected from the current bid or ask.

## Metrics

For every instrument, the worker retains only cumulative state. It does not retain the complete event history.

### Last traded price

The price of the most recently generated trade.

### Bid-ask spread

```text
ask price - bid price
```

### Trading volume

```text
sum of trade quantities
```

Bid and ask quantities do not contribute to trading volume.

### VWAP

```text
sum(trade price * trade quantity)
---------------------------------
       sum(trade quantity)
```

Prices are generated and accumulated in integer cents. Values are rounded only for display.

### Order-book imbalance

```text
bid quantity - ask quantity
---------------------------
bid quantity + ask quantity
```

A metric is unavailable when its denominator is zero.

## Producer settings

| Setting           | Default |       Range |
| ----------------- | ------: | ----------: |
| Instrument count  |       5 |        1-50 |
| Updates per batch |     100 |     1-1,000 |
| Batch interval    |  500 ms | 50-2,000 ms |

All settings must be integers.

Editing the form does not change the active producer. Apply starts a new run, clears the old metrics, and resumes generation if the previous run was paused.

Applied settings are stored in local storage and synchronized across open app tabs. A newly opened or reloaded tab starts its producer with the most recently applied settings.

## Performance

At the maximum configuration, the producer may generate:

```text
1,000 updates every 50 ms
= 20,000 updates per second
```

Every update contributes to volume and VWAP. The worker sends aggregated snapshots to Angular no more frequently than approximately every 100 ms, avoiding unnecessary UI rendering.

## Stale-run protection

Every run has a monotonically increasing `runId`.

All commands and worker events include this identifier. The Angular service ignores messages whose `runId` does not match the current run, preventing delayed results from overwriting newer state.

## Key design decisions

### Why AssemblyScript?

AssemblyScript produces a candidate-written WebAssembly module while keeping the toolchain close to the frontend ecosystem. The random number generation, stateful price evolution, and batch generation all execute inside Wasm.

### Why a Web Worker?

Generation and aggregation do not run on the browser's main thread, keeping the interface responsive at high update rates.

### Why aggregate inside the worker?

Sending every event to Angular would create unnecessary structured-clone and rendering overhead. Aggregating in the worker keeps all trades accurate while reducing UI traffic.

### Why use `setTimeout` instead of `setInterval`?

A recursive timeout schedules the next batch after the current batch has completed. This prevents callbacks from accumulating when processing takes longer than expected.
